# Case study 設計規範：結構層 vs 個性層

這份文件是對照「巢居 Nest Stay」跟「北捷 Metro」兩個已完成的 case study 實際 code 之後，整理出來的規範。目的：往後每接一個新專案（第三個、第四個…）時，能直接沿用同一套判斷邏輯，不用每次重新決定「這個該跟其他專案一樣，還是可以自己客製化」。

---

## 一句話結論

> **系統、節奏、材質統一；主題、強調色配比、招牌動效可以變。**

換句話說：使用者換頁到不同專案時，應該感覺「這是同一個人做的作品集」（結構層一致），但同時感覺「這一頁在講一個不一樣的故事」（個性層有變化）。

---

## 結構層（跨專案必須統一）

這些是兩個專案已經在共用、而且**不該**因為專案不同而改變的東西：

### 1. Design tokens（`globals.css`）
- 色票：`primary-orange #FF520D`、`secondary-blue #0D21FF`、`accent-pink #FF5BC0`、`grey-50~900` 灰階
- 字體：內文/標籤用 Nunito，大數字/展示型文字用 Fredoka One
- 這些 token 兩個專案都直接引用，沒有另外開新的顏色變數 — **繼續保持**，新專案也不要為了「這個專案要不一樣」另外開色票

### 2. 共用元件（`components/design-system/`）
`Typography`、`Tag`、`PhoneFrame`、`SlideIn`、`FadeIn`、`Navbar`、`Footer`、`BackToTop`、`DoorReveal`、`SectionKicker` — 新專案優先重用這些，不要每個專案重刻一套按鈕/卡片元件。

### 3. 版面骨架慣例
- 每個 section 的標頭固定順序：小標籤（eyebrow，大寫+letter-spacing+一個小色塊/icon）→ 標題（h2/h3）→（可選）一段 intro → 分隔線
- 手機版跟電腦版是**兩棵完全獨立的 DOM 樹**（`md:hidden` / `hidden md:flex`），不是同一棵樹硬用 responsive class 撐出來的 — 兩個專案都這樣做，因為手機版內容順序、卡片數量常常跟電腦版不一樣，硬共用 tree 會越改越亂
- 卡片陰影統一用暖色調、大範圍暈開的公式：`shadow-[0px_8px_12px_rgba(64,50,42,0.06),0px_1.5px_1.5px_rgba(64,50,42,0.04)]`（Metro 已經在多個 section 重複用這組值）— 之前巢居部分卡片用的是冷灰陰影，之後統一的話可以考慮對齊這組
- 卡片 hover：`whileHover={{ y: -2~-4 }}` + spring（stiffness 300 / damping 20）

### 4. 動效的「物理手感」
- 進場動畫預設用 `SlideIn`（spring, stiffness ~90-120, damping ~16-18），不要 linear easing
- 數字類統計一律用 CountUp（0 跑到目標值，`duration` 抓 1.2–1.4s，`ease: easeOut` 或自訂 cubic-bezier）——這個技術兩專案都各自寫了一份（Nest Stay 的 `ScoreCard`/`AverageScore`，Metro 的 `CountUpValue`），**下一個專案可以考慮把這個抽成 `design-system` 裡的共用 hook**，減少重複邏輯
- `prefers-reduced-motion` 一律要處理（已有的先例：Closing 的環境動畫都有做這層保護）

## 個性層（依專案調整，鼓勵有差異）

這些不但可以變、而且**應該**變，因為它們是「這個專案在講什麼故事」的一部分：

### 1. 招牌動效（Signature Motion）— 已經在 Metro 建立的慣例
Metro 每個 section 都有一個**跟內容意義綁在一起、不重複使用**的招牌動效，而不是每個 section 都套同一種裝飾：
- `Results` 用 `RadarPing`（雷達脈衝）— 呼應「成果驗證」的「持續監測」感
- `DesignPrinciples` 用 `ConvergeCard`（左右交錯往中間收斂）— 字面呼應「研究洞察**收斂**成設計原則」
- `Closing` 用 `DotDrift` + `MetallicSheen` + `OrbitRings` — 呼應「金屬感科技」的收尾語氣

巢居這邊其實也已經在做同樣的事，只是還沒有像 Metro 這樣明講：
- `InformationArchitecture` 的「流動箭頭」呼應「資訊架構的資料流」
- `WhyThisProject` 的「四步驟漸進聚焦」呼應「觀察→假設→驗證→架構推導」的推理過程

**往後新專案的做法**：先問「這個 section 在敘事上最想強調的感覺是什麼」，再決定招牌動效長怎樣，而不是先決定「這裡要有個科技動效」再隨便套一個。同一個招牌動效**不要跨專案重複用**（例如 RadarPing 只屬於 Metro 的 Results，不要直接搬到巢居的某個 section），這樣每個專案才會有自己的記憶點。

### 2. 強調色的「配比」與「主導色」— 回應你的具體問題
兩個專案色票完全一樣（orange / secondary-blue / accent-pink），這個決定**不需要改**——同一份作品集用同一套色票，反而會讓人感覺「這是同一個人的成熟設計系統，被有意識地套用在不同題目上」，比每個專案各自換一套顏色更專業、更不容易亂。

但目前兩個專案在色票**用法**上其實已經有一點差異，只是沒有刻意強化：
- 巢居：橘色是絕對主導色（badge、kicker、CTA、hero mockup 邊框都是橘），藍色只在「User Testing」標籤跟 Closing 背景出現，粉色幾乎沒用到
- 北捷：藍色份量明顯更重（`DesignPrinciples` 01/03 卡是藍、Closing 背景也是藍），粉色也比巢居用得多（`DesignPrinciples` 02/04 卡、`Results` 的服務指標）

建議往後**不要新增色票**，而是刻意放大這個已經存在的差異，讓「主導色」變成專案識別的一部分：
- 巢居＝橘色主導（貼合音樂祭/社群/熱情的主題）
- 北捷＝藍色主導（貼合交通/基礎建設/信賴的主題）
- 粉色維持兩個專案共用的「特殊強調/次要重點」色，不當主導色

這樣使用者不用看到專案名稱，光看色彩配比就能感覺「這兩頁調性不一樣」，但配色系統本身完全沒有變多，不會有你擔心的「視覺太亂」問題。

### 3. 敘事節奏（Pacing）
Metro 目前每個 section 都是 `min-h-screen` 滿版投影片式的閱讀節奏（一次一個重點，捲軸像在翻頁）；巢居目前大部分 section 是連續捲動、沒有強制滿版高度（只有這次特別要求的 `WhyThisProject` 例外）。

這個差異目前是**無意間**造成的，不是刻意設計決策。建議往後：
- 如果一個專案的敘事本身比較像「一步一步引導使用者看完一個論證」（像 Metro 的研究→原則→成果），滿版投影片式的節奏比較合適
- 如果一個專案比較像「連續的產品故事線」（像巢居的併團流程），連續捲動比較合適
- 兩種都可以，但同一個專案內部要一致（不要同一頁有些 section 滿版、有些不是，除非像 `WhyThisProject` 這種有明確理由的例外）

### 4. 局部裝飾細節
像 Metro `Results` 的 `DotGrid`／`PlusMark`，或巢居 Closing 的菱形紋理飄移，這種「一次性的小彩蛋」本來就該每個專案自己決定要不要有、放在哪裡，不用強求一致。

## 給下一個專案的檢查清單

開新專案時，照這個順序決定：

1. **色票**：直接沿用 `globals.css` 現有 token，不新增顏色
2. **主導色**：選一個既有色票（橘/藍/粉三選一，或以其中一個為主+另一個為輔）當這個專案的識別色，貼合這個專案主題
3. **元件**：`design-system/` 資料夾裡有的先用，沒有才新增（新增後要更新這份文件的「共用元件」清單）
4. **版面骨架**：section header 順序、手機/電腦分樹、卡片陰影公式、hover 手感照抄結構層
5. **敘事節奏**：這個專案是「投影片式」還是「連續捲動式」？選一個，整頁貫徹
6. **招牌動效**：每個 section 挑一個跟內容意義相關、沒被其他專案用過的動效，不要為了有動效而有動效
